The committed projection is stale
  store.facts in this directory describes a 746-line, 71-defn, 0-defrecord
  fram.store and does not reproduce from live fram. Its `triple` signature
  reads `t1: Any`, a spelling that exists in no fram revision: beagle 0d043c06
  hand-renamed slot0/slot1/slot2 to t1/t2/t3 inside the derived evidence
  instead of re-deriving it, while fram's own rename (3275dea) simultaneously
  retyped those parameters to `Term`. source.sha256 is older still — it pins
  the pre-Core-migration types.bclj.

  The driver reads fram:src/fram/types.bgl + fram:src/fram/store.bgl and fails
  on the difference. It no longer falls back to this file; committed-facts mode
  is NATIVE_SLICE_COMMITTED_FACTS=1 and stamps a MODE line into report.txt.
  Clearing the drift is a cross-repo evidence refresh, not a driver change.

Why the dependency is in the program
  store.bgl declares no record; every type in its signatures is a fram.types
  record. Projected alone, its typed program fails types-refs-closed? and the
  source-to-typed pass rejects. The source program therefore carries both ASTs
  and names fram.store as its module.

Named gaps
  1  Bodies are not in the source program. The fact projection carries record
     and defn DECLARATIONS only, so no store body was ever presented to the
     lowering. Every one of the 71 store functions is a standing
     TODO-NATIVE-FUNCTION-BODY obligation; program-functions and program-abis are
     both 0 and typed-to-native is PENDING, not COMPLETE.
  2  obligation-program closed-layouts FAILs on the full program: shapes that need
     an explicit reference edge stay unclosed. The C17 projection restores the
     obligation by excluding them, which is why obligation-projection passes.
  3  The restricted C17 vocabulary admits 5 of 57 program types. Every shape
     store.bgl itself contributes -- (Vec T), closed (U T Nil), Text/Keyword
     atoms, map-entry vectors, (Atom T) references -- is outside it, so the
     emitted C is byte-identical to native-core/validation/slice-types-full's.
     The store-specific evidence in this slice is the frozen program, the typed
     signature surface, and the obligation ledger, not new C.
  4  main.c is hand-written: the materializer emits types only, so the runtime
     check is the layout claim under ASan/UBSan, never a store body.
