What the committed projection pins
  store.facts is the projection of fram at 6863f0a: fram:src/fram/types.bgl
  last moved at 28664e2, fram:src/fram/store.bgl at 4a3066a. source.sha256
  carries those two file hashes, types first.

  drive.sh re-derives from the LIVE fram checkout on every run and fails on any
  difference from store.facts, so an edit to either fram file reds this driver
  until the snapshot here is refreshed. Committed-facts mode is
  NATIVE_SLICE_COMMITTED_FACTS=1; it proves only that the committed projection
  still lowers, never that it matches live fram, and stamps a MODE line into
  report.txt. Clearing drift is a cross-repo evidence refresh, not a driver
  change.

Why the dependency is in the program
  store.bgl's own three records are results (TermStoreLoadResult,
  TransactionReplayResult, TransactionFramesResult); every other type in its
  signatures is a fram.types record. Projected alone, its typed program fails
  types-refs-closed? and the source-to-typed pass rejects. The source program
  therefore carries both ASTs and names fram.store as its module.

Named gaps
  1  Bodies are not in the source program. The fact projection carries record
     and defn DECLARATIONS only, so no store body was ever presented to the
     lowering. Every one of the 127 declared functions (96 fram.store,
     31 fram.types) is a standing TODO-NATIVE-FUNCTION-BODY obligation;
     program-functions and program-abis are both 0 and typed-to-native is
     PENDING, not COMPLETE.
  2  obligation-program closed-layouts FAILs on the full program: shapes that need
     an explicit reference edge stay unclosed. The C17 projection restores the
     obligation by excluding them, which is why obligation-projection passes.
  3  The restricted C17 vocabulary admits 5 of 87 program types. Every shape
     store.bgl itself contributes -- (Vec T), closed (U T Nil), Text/Keyword
     atoms, map-entry vectors, (Atom T) references -- is outside it, so the
     emitted C is byte-identical to native-core/validation/slice-types-full's.
     The store-specific evidence in this slice is the frozen program, the typed
     signature surface, and the obligation ledger, not new C.
  4  main.c is hand-written: the materializer emits types only, so the runtime
     check is the layout claim under ASan/UBSan, never a store body.
