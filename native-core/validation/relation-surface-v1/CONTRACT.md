# Relation-centered surface v1 validation contract

This is a validation-local, non-default source-profile experiment. It does not
register `#lang beagle/rel`, modify the production parser, or change bare
`#lang beagle`. Tracked whole-file `.brel` projections are first-class inputs
for the prototype; generated Lisp/Core exists only in driver scratch space.

## One projected shape

The v1 structural grammar is deliberately closed:

```text
source   := "(" LITERAL PLUS LITERAL ")" EQUALS LITERAL EOF
PLUS     := "+" | "plus"
EQUALS   := "=" | "equals"
LITERAL  := INT | BOOL
INT      := a canonical signed 64-bit decimal integer
BOOL     := "true" | "false"
```

Whitespace, comments, and line layout are reader trivia. The validation wrapper
creates a bounded `ReaderRequestV1`; the production shared datum reader returns
an accepted `ReaderProductV1`. The bridge consumes that accepted event stream
rather than re-reading source itself. Decimal atoms currently arrive as
symbols, so the bridge still validates their canonical spelling and range.

Both of these source projections:

```text
(2 + 5) = 7

(
  2
  plus
  5
)
equals
7
```

project deterministically to the ordinary Core expression:

```clojure
(= (+ 2 5) 7)
```

The result is *projected Core*, not accepted or checked Core. The existing
checker alone decides whether a structurally projectable expression is typed.
For example, `(2 + true) = 7` projects successfully and is then rejected by the
checker with `E002` because argument 2 to `+` is `Bool`, not `Number`.

Equality therefore has ordinary eager Boolean semantics in this experiment.
No relation, proposition, constraint, variable, mode, or search node survives
to checking or Native lowering.

## Semantic boundaries

| Surface category | v1 decision |
| --- | --- |
| expression | Ordinary evaluation through existing checked Core. |
| proposition | Preserved semantic content in the separate proposition-profile experiment. |
| query | Explicit bounded open-relational execution in that separate profile. |
| assertion | Separate Store admission; never implied by reading, projection, checking, or derivation. |

Open `?x`, `query`, `solve`, `assert`, `fact`, `law`, `rule`, `goal`, malformed
integers (including overflow), and every unsupported shape are hard rejections.
A bridge rejection writes no Core, projection receipt, or Core map. This fixture
contacts no Store, creates no world, asserts no proposition, and requests no
effect beyond bounded local file reads and scratch-file writes through
`host.fs`.

## Reader, source, and Core authority

The bridge input retains three things together:

```text
logical authored path + ReaderRequestV1 + accepted ReaderProductV1
```

`ReaderProductV1` alone does not retain the logical path, raw trivia, or all
source authority. The request binds the exact payload and provenance; the path
keeps the authored file first-class for this bounded relation-surface
experiment. Before projection, the bridge recomputes the path-and-payload
projection identity and requires it to equal the request's provenance identity.
A product/request from path A cannot be relabeled as path B.

The identities intentionally answer different questions:

- source-content identity covers exact authored payload bytes;
- source-projection identity covers logical path plus payload content;
- reader-IR and reader-provenance identities come from the accepted reader
  product;
- ordinary-Core expression identity covers the bridge rule and canonical Core
  expression, excluding source path and provenance;
- canonical-module identity covers the bridge rule and exact generated module
  bytes, also excluding source path and provenance; and
- Core-map identity binds the canonical module, reader IR, logical authored
  path, reader provenance, and exact generated-to-authored map; while
- the logical `.bgl` source ID derives from canonical-module identity, so a
  random scratch path does not enter bridge or exact-byte bundle identity.

Consequently, different paths, layout, and operator spellings retain distinct
projection, reader, provenance, and Core-map identities and distinct receipt
bytes, while sharing byte-identical Core and equal Core expression/module
identities. Repeating the same projection must reproduce every emitted byte.
The driver also submits the
exact generated bytes through `ast-bundle` and requires the content-derived
logical Core source ID to survive checking.

Core expression/module identity is not a claim of fully checked semantic
identity. Checked meaning additionally depends on resolved interfaces,
checker/schema/stdlib rules, and actual semantic dependencies.

## Composed diagnostics

The reader source map addresses canonical reader-event encoding, not generated
Core. Relation lowering reorders operators and operands, so the bridge creates
a separate Core map. Its entries partition every generated byte, are ordered by
generated position, may point nonmonotonically into authored source, and mark
module glue and spacing as synthetic.

The deliberate `E002` probe uses the checker's unchanged V2 diagnostic. Its
current generated anchor covers the whole `(+ 2 true)` call. A sibling authored
diagnostic projection preserves every overlapping origin: the five exact
authored spans (including `true` at `[5,9)`) and the fact that synthetic spacing
also overlaps. It does not mutate the checker's diagnostic or falsely blame
synthetic-only module bytes on the nearest authored token.
Native materialization independently refuses the same ill-typed Core before
publishing an executable or artifact.

## Current gaps this does not design away

Beagle's compiler AST, compiler fact projections, and Store Terms remain
separate current surfaces. This experiment records that boundary; it does not
pretend Store triples are compiler expressions or that relational derivation is
Store assertion.

Production `parse-program` still cannot consume `ReaderProductV1` directly.
This validation writes projected canonical Core to scratch and re-enters the
ordinary parser through an exact-byte request. Whole-file `.brel` inputs remain
the prototype authoring authority; capsule-qualified fenced source is the next
bounded rung, and registered `#lang` dispatch remains later. None of those gaps
is claimed as solved here.

The final CLI Native execution still consumes the scratch `.bgl` path. It
proves that projected bytes execute through Native Core, but not that the
content-derived logical source ID survives the Native CLI or that checked
binding identity is projection-independent.
