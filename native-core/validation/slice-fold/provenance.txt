named gaps
  1 no fold function reaches a native body. typed-to-native implements exactly
    identity, checked-add-i64, and const-zero-i64; transaction-frame,
    max-sequence, project, fold!, and refold! carry no `native-op` fact, so each
    stays a TODO-NATIVE-FUNCTION-BODY obligation and the world lowers zero
    functions and zero ABI declarations (legal-abi receipt obligation PENDING).
  2 closed-layouts FAILS on the Text and Keyword atoms. layout-shape-for gives a
    TextKind atom a ReferenceShapeV0, and layout-shape-exact? accepts only a
    ScalarShapeV0 with a bit width for an AtomType. Both types are builtins, so
    every real module slice hits this, not just fold.
  3 native.c11 is unusable as the materializer: its cross-namespace `match`
    forms emit unqualified variant symbols that fail to resolve in the clj
    target, and the file is graph-upstream so the text arm is refused. This
    slice ships native.fold-c17 instead; folding it back into c11 is a graph
    edit, not a text edit.
  4 vector element types and reference targets are erased to `const void *` /
    `void *` in the C projection; element stride survives in the layout and in
    the emitted comment, the element type does not round-trip through the header.
  5 union variant payload offsets are per-variant in Native Core and single in
    C. They agree for every shape here (each variant offset is align-up(tag,
    variant alignment), so the widest variant sets the union offset), and the
    generated assertion checks only that widest offset.
  6 `T?` optionals and raw `Any` are normalized in the source projection: `T?`
    to a two-arm closed union, `Any` to SliceValue (LOWER-CLOSED-RAW-ANY).
  7 OutcomeType is not materialized; fold reaches no outcome-typed value.
